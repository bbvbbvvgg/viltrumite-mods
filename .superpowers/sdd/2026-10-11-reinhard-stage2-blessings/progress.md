## Rulings

- Ruling: stage 1b decisions were taken from the PR #28 body and `SESSION.md` — the plan references `.superpowers/sdd/2026-10-11-reinhard-stage1b-visuals/progress.md`, which does not exist on any branch — cost if wrong: a 1b decision recorded only in that missing ledger is not honoured.
- Ruling: the Phoenix HUD icon sits left of the ability column at the row of the first mode icon (`icons[0].x`, below the Reid bar), with the remaining time as a half-size `m:ss` label to its right — the plan says "under the mode icons", but the ability bar is a vertical column at the right edge, so "under" has no room; the chosen spot keeps the icon next to the mode icons — cost if wrong: icon moves by a few pixels, layout-only.
- Ruling: Phoenix flames reuse the existing `HeroFx` kinds (flash at origin and at the new point + launch with fire material); the client `PhoenixFlameVfx` is state-driven (it reacts to the rise of the Phoenix cooldown in the public snapshot) — no new FX packet kind was added — cost if wrong: an observer that joins mid-cooldown sees no flames (cosmetic).
- Ruling: one commit per plan task (the user's rule) instead of the plan's two commits per task (`feat(hero): …` + `feat(reinhard): …`); the commit message names both parts — cost if wrong: history granularity only.
- Ruling: Phoenix and Adaptation state: the Phoenix cooldown lives in `PersistentCooldowns` (player persisted NBT, survives hero change and death); Adaptation is saved with the hero state but `respawnCopy()` drops it, so death clears acquired immunities — spec §4 — cost if wrong: immunities survive death.
- Ruling: the plan's flag `PARRY` is the existing `ReinhardFlags.PARRY_POSE` (bit 5, reserved in stage 1a) — no new bit — cost if wrong: none (naming only).
- Ruling: the parry is decided in `absorbIncoming` before the resist (plan) for every non-divine hit whose direct entity is the living attacker itself (not self), no projectile (direct entity or `is_projectile` tag) and no explosion tag; the front cone uses the head yaw (where he looks), horizontal only; an attacker exactly inside his column is not parried — cost if wrong: a hit from straight above/below at zero horizontal distance gets resisted instead of parried.
- Ruling: the parry pose is a real-time weight pulse (`ParryPulse`, K_IN 40 / K_OUT 10, separate third- and first-person instances) over a hold-on-last-frame `parry` clip; first person turns the main arm's ModelPart for the draw and restores it — no new mixin — cost if wrong: animation feel only.
- Ruling: REFLECT re-aims a fireball's power vector along the new velocity (magnitude kept) instead of a plain reversal — the plan says "reversed"; with an owner the reflected velocity points at the owner's eyes, not straight back, so a reversed power would curve the fireball off the aim; without an owner both are the same — cost if wrong: a reflected fireball flies at the owner instead of curving back along its old line.
- Ruling: the deflect side is "away from the body centre" when the centre is more than 0.1 block off the flight line, random otherwise (the plan says both "random side" and "away from the body centre"); the turn axis is world up made perpendicular to the velocity (x for a vertical drop), so a deflect swings sideways and never lobs up — cost if wrong: deflect direction only.
- Ruling: a projectile owned by the hero himself is never answered (PASS) — after a reflect he is the owner, and his own shots never hit him in vanilla anyway — cost if wrong: none in practice.
- Ruling: every response is re-checked at the end of the level tick (`HeroProjectiles.tickPending`): llama spit (and any class that moves with the velocity read before the hit check) overwrites the new velocity in its own tick, so it is re-applied there and the projectile pushed out of the hero's box again — cost if wrong: llama spit keeps flying through him.
- Ruling: an accepted air step is confirmed WITHOUT a motion packet — the plan's Interfaces step 3 says "server sets velocity + hurtMarked (vanilla motion packet)", its Risks say "the server must not set velocity for them (double jump)"; with latency a late authoritative 0.62 arrives when the client is already further along the arc and boosts a second time. The server updates only its own copy of the velocity, the counter and the fall distance; a refused press sends a motion packet (server x/z, min(y, 0)) plus `AirJumpSyncS2CPacket(used)`, no FX — cost if wrong: a desynced client keeps a predicted step until its next ground touch (the counter still re-syncs).
- Ruling: observers get the air-step ring from the same `AirJumpSyncS2CPacket` (flag `step`, sent to trackers only), not from `HeroFx.launch` — the launch FX is a ground dust ring with camera shake and also reaches the stepping player, who already drew the ring at the prediction; the ring is generic (`client/render/vfx/AirStepVfx`) because the seam is not Reinhard's. `ReinhardFlags.AIR_STEP_PULSE` stays reserved (no air-step pose clip in this stage, see deferred minors) — cost if wrong: observers see a white ring instead of a dust puff.
- Ruling: new hook `HeroDefinition.onAirStep(ServerPlayer)` (default no-op) for the hero's own step sound — the plan's seam lists only `airJumps`/`airJumpVelocity`, but the generic `HeroAirJump` cannot play Reinhard's sound without a hero branch — cost if wrong: one extra default method on the seam.
- Ruling: `AIR_STEP_VELOCITY` stays 0.62 as the plan's number; with vanilla gravity/drag that is ≈2.5 blocks per step from a standstill (`HeroSuperJump.apex(0.62)`), not the plan's "≈1.9"; `stepHeightAbout2` accepts 1.8–2.6 — cost if wrong: one rules constant to lower (0.54 ≈ 1.9 blocks).
- Ruling: `ReinhardHero.canAct` allows JUMP and AIR_STEP while alive and not anchored (stage 1 refused every action but MODE_CYCLE, which made the super jump a no-op on the server) — cost if wrong: none.
- Ruling: the client takes no air step while fall flying (an elytra start uses the same key) and never on the tick vanilla took the ground jump (ground at tick START) — cost if wrong: an elytra wearer can't air-step.
- Ruling: `WindReadingClient.colorOf` returns -1 for "not ours", not the plan's 0 — the code contract of `OutlineTargets` is "-1 = no source claims it" and 0 would be a valid black outline that blocks Iron Man's and Homelander's sources — cost if wrong: none.
- Ruling: `WIND_COLOR` lives in the client class `WindReadingClient`, not in `ReinhardRules` as the plan lists — the user's rule keeps visual constants in client classes and gameplay numbers in `ReinhardRules` — cost if wrong: one constant moves.
- Ruling: recent player attackers are recorded in `absorbIncoming` (every hit, parried/absorbed/divine included), not in `onHurt` as the plan says — a parried hit never reaches `onHurt`, and a player who swings at his back and gets parried is exactly the threat to feel — cost if wrong: a fully parried attacker is outlined for 5 s.
- Ruling: "projectile flying toward him" = a projectile within the radius whose velocity is within ~25° of the line to his chest (cos > 0.9); its owner counts as hostile; the projectile itself is not outlined — cost if wrong: a stray shot nearby outlines its shooter.
- Ruling: the THREATS section is cleared on death and hero change, not on disconnect (the client drops its sections on logout; no packet to a closing connection) — cost if wrong: none.
