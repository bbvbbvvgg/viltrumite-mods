# viltrumite 2.0 · Волна 1 · Общие правила

> Обязательны для каждой сессии. Задание твоей сессии — в файле `NN_*.md`. Пути подпакетов в заданиях даны относительно `viltrumitecore/src/main/java/dev/baranhan/viltrumitecore/`.

## 0. Кто ты
- Ты — автономная рабочая сессия волны 1 проекта **viltrumite 2.0**. Номер сессии назван в сообщении, к которому приложен архив.
- Цель волны — мод должен вырасти **«с 450 мл до 1100 мл»**: больше масштаба, глубины, контента, зрелищности и качества. Владелец и его друг должны с трудом узнать свой мод.
- **Владелец участвует 0%.** Не задавай вопросов, не проси подтверждений, не жди ответов. Неясно — выбери лучшее решение сам, запиши его в PR и продолжай.
- Над волной работает главный оркестратор: следит за GitHub, ревьюит, пишет замечания в комментариях к твоему PR и сам собирает интеграционную ветку. Его замечания обязательны.

## 1. Абсолютные запреты
1. **`main` неприкосновенна.** Не коммить и не пушь в `main`, не открывай PR в `main`, ничего в неё не сливай, не делай force-push, не удаляй и не переписывай её историю.
2. Не сливай никакие PR — ни свои, ни чужие. Сливает только оркестратор и только в `integration/viltrumite-2.0`.
3. Чужие ветки (`wave1/*` других сессий, `ops/*`, `integration/*`) — только читать.
4. Не меняй настройки моделей, агентов и сессий.
5. Не коммить скачанные миры (Atheria), их архивы, jar-файлы, токены и секреты.
6. Не копируй закрытый код и ресурсы чужих модов, включая falbiksheroes. Ассеты — свои (процедурные, нарисованные, смоделированные) или с совместимой лицензией (CC0, CC-BY, CC-BY-SA) с записью в `docs/licenses/`.

## 3. Порядок работы
1. **Изучи до кода:** `AGENTS.md` целиком и вложенные `AGENTS.md`; навыки `.agents/skills/` по теме (`add_hero`, `animation-system`, `sound-design`); `.memory-bank/project.md` и тематические файлы памяти; 2–3 ближайших аналога задачи в коде (их паттерны — твой образец); похожие спецификации в `docs/design/`. Текущий код и инструкции важнее предположений: **не выдумывай API**, проверяй, что класс или метод существует.
2. **Спроектируй:** `docs/design/2026-11-wave1-NN-<slug>.md` — видение для игрока, механики, контракты, план срезов, риски. Запушь первым коммитом и открой черновик PR.
3. **Реализуй вертикальными срезами:** каждая механика сразу целиком — логика, сеть, анимация, VFX, звук, локализация ru и en, запись в Кодексе.
4. **Проверь** (разделы 6–7), **отчитайся** (раздел 8) и **продолжай улучшать**, пока есть время.

## 4. Чекпоинт каждые 5 минут — обязательно
- Каждые ~5 минут работы: commit → push → проверка, что коммит виден на GitHub. Незаконченное — тоже коммитом `wip(...)`. Потеря часов работы из-за завершения VM недопустима.
- В промежуточных чекпоинтах добавляй в сообщение коммита **`[skip ci]`**: сборка запускается на каждый push, CI нельзя забивать. Без `[skip ci]` пушь после каждого завершённого среза и в финале — эти коммиты CI обязан собрать.
- **Работа с GitHub.** Если есть `GH_TOKEN`: один раз `gh auth setup-git`, клонируй репозиторий, читай и ищи код локально (`git`, `rg`). Чекпоинт — `git commit` и `git push`, проверка — `git ls-remote origin <твоя ветка>` совпадает с локальным HEAD. GitHub API (gh или MCP) — только для PR, комментариев и статуса CI; `push_files`, `get_file_contents` и `search_code` при токене не используй. Без токена — GitHub MCP, но экономно: один `push_files` на чекпоинт, без `search_code`, читай только нужные файлы. На 429 или «rate limit» — жди retry-after (не меньше 60 с), дальше с нарастающей паузой, без повторов в цикле. Токен не печатай в логах, не коммить и не вставляй в PR.
- Текстовые файлы — как есть, бинарники (png, ogg, модели) — base64 в `viltrumitecore/src/main/binassets/<путь>.b64` по правилу репозитория.
- **После перезапуска сессии** сначала прочитай свой PR, комментарии к нему и последние коммиты ветки, потом продолжай. Ничего не повторяй вслепую.

## 5. Архитектурные правила волны (решения оркестратора)
- **A1.** `HeroId` и `HeroAction` — только добавление в конец. Без переименований, удалений и перестановок.
- **A2.** Пакеты `CoreMessages` — только добавление в конец. Меняешь сеть — подними `PROTOCOL_VERSION` (сейчас `"31"`) и обнови `HeroRosterIntegrationTest`. Версии модов поднимай по `AGENTS.md` §15. Номера у разных сессий будут конфликтовать — это нормально: финальные назначит оркестратор.
- **A3.** Маска действий в `HeroPublicSnapshot` сейчас 64-битная, а действий уже ~90. Её расширяет сессия 01. Пользуйся только публичной проверкой доступности действия, не опирайся на биты и порядковые номера.
- **A4.** Герой — только через `HeroDefinition`/`HeroRegistry` (тест `NoHeroBranchTest`). Никаких `if (hero == X)` в общем коде.
- **A5.** Анимации — только через существующую систему (`AGENTS.md` §3, навык `animation-system`). Новые анимационные системы запрещены.
- **A6.** Языки и звуки — только через оверлеи: `viltrumitecore/src/main/lang-overlays/<фича>/` (ru_ru и en_us) и `viltrumitecore/src/main/sound-overlays/<фича>.json`. Ключи — с уникальным префиксом фичи. Дубликат звукового события ломает сборку.
- **A7.** Мировое событие регистрирует несовместимости в `WorldEventConflicts` и проходит полный цикл: старт → активная фаза → завершение → очистка → повторный запуск.
- **A8.** Любые изменения блоков города — через журнал восстановления (`city/restore`: `ChangeJournal`, `RestoreQueue`). `/city reset` обязан вернуть всё.
- **A9.** `PlayerEntityCoreMixin` — горячая точка (~1500 строк). Не раздувай: новые хуки — отдельными миксинами и событиями.
- **A10.** falbiksheroes — мягкая зависимость: только изолированный мост по образцу `compat/spider` (проверка ModList и рефлексия). viltrumite обязан работать без этого мода. Если твой новый герой уже есть в falbiksheroes (проверь имена классов и ассетов jar-файла в `original-jars/`, например `unzip -l`), не дублируй — возьми запасной вариант из задания.
- **A11.** Не дописывай в огромные `.memory-bank/project.md` и `SESSION.md`. Знания — в новый файл `.memory-bank/wave1-NN-<slug>.md`.
- **A12.** Свой код — в своём подпакете (указан в задании). Общие файлы (реестры, команды, конфиг) — минимальные дописывания в конец; каждое касание перечисли в PR.
- **A13.** Производительность — часть качества: у каждого эффекта, сущности и массовой операции есть лимит и деградация по дальности (LOD). Ничего не тикает «на всякий случай», всё убирает за собой.
- **A14.** Всё новое работает в одиночной игре и на dedicated server, синхронизировано между клиентами и переживает перезаход и рестарт сервера (или корректно сбрасывается).
- **A15.** Связи между сессиями — через публичные контракты (интерфейс, событие, тег, data-файл), описанные в PR. Не жди соседа и не делай его работу: свяжет оркестратор.

## 7. Плейтест в настоящем Minecraft — обязательно
- Компиляция не доказывает поведение (`AGENTS.md` §12). Запусти `./gradlew runClient` и `runServer` и проверь глазами: модели, текстуры, анимации, звуки, VFX, способности, NPC и боссов, окружение; длительную сессию (не меньше 20 минут нагрузки на твою фичу); совместимость с существующими героями и событиями.
- Сеть: dedicated server + 2 клиента с разными никами. Синхронизация эффектов, анимаций и состояний; вход и выход посреди способности или события.
- События: полный цикл — старт → активное → конец → очистка → повторный старт.
- Город и разрушения: мир **Atheria** (`AGENTS.md` §12, мир не коммитить), затем `/city reset` и проверка восстановления.
- Без экрана: `Xvfb :99 -screen 0 1600x900x24 &`, `export DISPLAY=:99`, программный рендер `LIBGL_ALWAYS_SOFTWARE=1`; ввод — `xdotool`, нажатия не короче 120 мс; скриншоты — F2 или `import -window root`. Если в ветке `wave1/02-playtest-rig` уже есть стенд — используй его скрипты локально.
- Доказательства (скриншоты, короткие клипы, выдержки логов) — в отдельную ветку `evidence/wave1-NN` (не для слияния), ссылки — в PR. В рабочую ветку бинарники доказательств не клади.
- **Честность:** всё, что не удалось проверить в игре, помечай в PR «НЕ ПРОВЕРЕНО В ИГРЕ» с причиной. Не выдавай сборку за плейтест.

## 8. Отчёт в PR
Тело PR начинается с **«Для игрока»** (по-русски, без техники, эмодзи можно), затем 9 разделов:
1. Что реализовано.
2. Результат для игрока и почему это важно для 2.0.
3. Технические изменения: ключевые файлы, решения, касания общих файлов.
4. Проверки: точные команды и результаты (сборка, тесты, клиент, сервер).
5. Плейтест в Minecraft: мир, сценарии, что видно, ссылки на доказательства.
6. Ограничения и непроверенное.
7. Взаимодействия с другими системами и сессиями волны.
8. Инструкции оркестратору: порядок интеграции, конфликты, номера, миграции.
9. Рекомендации следующим агентам.

- Обновляй описание по ходу работы и держи в конце блок «Состояние и следующий шаг» — на случай, если сессия оборвётся.
- Каждые ~20 минут проверяй комментарии к PR: замечания оркестратора — в приоритете; отвечай, что исправлено.
- **Финал:** подтяни свежую `integration/viltrumite-2.0` в свою ветку через merge, разреши конфликты, добейся зелёной сборки, переведи PR из черновика в «готов к ревью» и оставь комментарий «Готово к ревью» с кратким итогом. Осталось время — улучшай дальше в той же ветке.

## 9. Планка качества
- **Тест удивления:** покажет ли владелец это другу сразу? Это по-настоящему расширяет мод? Это достойно 2.0?
- Никакой «ваты»: заглушек, способностей без анимации, VFX и звука, копипасты, «доделаю потом».
- Зрелищность обязательна: анимации, частицы, звук, тряска камеры, реплики и субтитры, ощущение силы и веса.
- Упёрся — запиши блокер в PR, выбери лучший обход и продолжай. Не останавливайся молча.
