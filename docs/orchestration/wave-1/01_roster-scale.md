- **Зона:** `hero/HeroPublicSnapshot` и его сериализация, связанные пакеты и тесты; новый `hero/roster/` при необходимости.
- **Не трогай:** логику конкретных героев.

## Для игрока
Ничего не ломается, когда героев 25+, а действий 200+: подсказки доступности, перезарядки и HUD верны у каждого героя, сеть не тормозит. Это фундамент волны: в ней 7 новых героев и десятки новых действий.

## Обязательно
1. Замени 64-битную маску `availableActions` масштабируемым представлением (например `long[]` или `BitSet`) без верхнего лимита. Убери исключение «has no bit in the 64-bit action mask».
2. **Публичный API снапшота сохрани совместимым по исходникам:** десятки сессий параллельно пишут код против текущего API. Нужен новый метод — добавь рядом, старый оставь.
3. Компактное сетевое кодирование (varint + битовый набор), подъём `PROTOCOL_VERSION`, обновление `HeroRosterIntegrationTest`.
4. Тесты: 256 синтетических действий, кодирование туда-обратно, граничные индексы 63/64/127/128, совместимость сохранений (если снапшот или его части сохраняются).
5. Аудит других жёстких лимитов для 25+ героев и 200+ действий: массивы по ordinal, слоты клавиш и хотбара, размеры пакетов, таблицы Кодекса и HUD. Критичное исправь, остальное перечисли в PR.
6. Контракт для авторов героев: `docs/architecture/hero-roster-scale.md` — как добавлять героев и действия и чего нельзя.
7. **Ядро исправления запушь рано** — в первые 60–90 минут, отдельным коммитом без `[skip ci]` — и отметь это в PR: оркестратор интегрирует его первым.
