# Волна 1 · Сессия 02 · Автоматический плейтест-стенд

> Статус: дизайн + план срезов. Ветка `wave1/02-playtest-rig`, PR в `integration/viltrumite-2.0`.

## Для игрока
Игрок стенд не видит. Он получает сборки, которые до выхода прошли настоящий Minecraft: dedicated server и два клиента с разными никами, все 14 героев, все мировые события и разрушение города с `/city reset`. Багов вечером меньше, тормоза видны заранее.

## Цель
Одна команда поднимает сервер и два клиента, прогоняет сценарий без рук и собирает отчёт: логи, скриншоты, TPS/MSPT, FPS/frametime, память. Любая сессия волны должна повторить это по `docs/playtest/rig.md` за 10 минут.

## Что уже есть в репозитории (переиспользуем, не дублируем)
- **QA-драйвер клиента** `client/hero/speech/qa/SubtitlePlaytest` за флагом `-Dviltrumitecore.subtitles.playtest=true`. Он читает команды из `<gameDir>/subtitle_qa.txt` каждые 5 тиков: `press`, `key`, `cmd`, `shot`, `cam`, `look`, `perfreset`/`perfstate` (`FrameProbe`: FPS, 1 %-low, p50/p99/max ms, GC, heap, частицы, сущности), `state` и десятки `*state`-проб. Стенд пишет в этот файл и читает строки `SUBPT` из лога клиента. Новый командный канал не нужен.
- **RCON** — `tools/city/rcon.py` (минимальный клиент). Стенд использует свой RCON-клиент в `tools/playtest/` с ожиданием ответа и таймаутом, по образцу этого файла.
- **Набор офлайн-клиента** `~/kit`: Xvfb + Mesa llvmpipe + xdotool + ScreenCapture (`client.sh`, `screen.sh`, `input.sh`).
- `tools/perf/atheria_bench.sh` — образец сценария поверх QA-драйвера.

## Архитектура стенда (`tools/playtest/`)
- `rig.py` — один Python-файл без сторонних пакетов (stdlib, Python 3). Подкоманды:
  - `rig.py up` — сборка (можно пропустить `--no-build`) → остановка всего → подготовка `run/` сервера (`online-mode=false`, `eula=true`, RCON, `level-type`, мир по выбору) → `runServer` → ожидание `Done (` → клиенты.
  - `rig.py run <сценарий.json>` — `up` + сценарий + `down` + отчёт.
  - `rig.py down` — аккуратная остановка (RCON `stop`, затем SIGTERM/SIGKILL по группам процессов, удаление сессий Xvfb).
  - `rig.py status`, `rig.py shot <client> <file>`, `rig.py cmd <server|cN> ...` — ручная отладка.
- **Клиенты без Gradle.** Один Gradle-демон на клиент съедает ~1,5 ГБ, на машине 4 ГБ два клиента так не влезают. Стенд один раз снимает реальную командную строку JVM клиента, которую строит ForgeGradle (`/proc/<pid>/cmdline` дочернего java при `runClient`), сохраняет её в `run-rig/launch-client.json` и дальше запускает клиентов напрямую: свой `-Xmx`, свой `--gameDir`, свой `--username`, `--quickPlayMultiplayer 127.0.0.1:<port>` (аргумент запуска 1.20.1). Сервер — так же (`launch-server.json`). После `build` пути классов те же, поэтому снимок остаётся верным; при изменении `build.gradle` стенд снимает его заново.
- **Каждый клиент — свой Xvfb** (свой DISPLAY и Xauthority-cookie), своя папка игры `run-rig/client-<ник>/`, свой лог. `options.txt` создаётся стендом: без онбординга доступности (`onboardAccessibility:false`), без музыки, низкая дальность прорисовки, пауза при потере фокуса выключена.
- **Каналы управления:** сервер — RCON; клиент — файл QA-драйвера (команды игрока, способности, пробы) и xdotool в его DISPLAY (удержание клавиш ≥120 мс, мышь); скриншоты — ScreenCapture из набора.
- **Память.** Перед стартом стенд считает свободную память. Второй клиент запускается, только если хватает (`--min-free-mb`); иначе прогон идёт с сервером и одним клиентом, а отчёт честно пишет «НЕ ПРОВЕРЕНО В ИГРЕ: второй клиент — не хватило памяти машины» с цифрами.

## Формат сценария (JSON)
```json
{
  "name": "smoke-heroes",
  "clients": ["Alpha", "Bravo"],
  "world": {"type": "flat"},
  "timeout_s": 1800,
  "steps": [
    {"server": "op Alpha"},
    {"client": "Alpha", "qa": "cmd hero set viltrumite"},
    {"wait": 2},
    {"key": {"client": "Alpha", "keys": ["w"], "hold_ms": 400}},
    {"expect": {"log": "server", "regex": "Done \\(", "timeout_s": 60}},
    {"shot": {"client": "Alpha", "name": "viltrumite_idle"}},
    {"metrics": "viltrumite"},
    {"include": "parts/hero.json", "vars": {"hero": "thor"}},
    {"foreach": {"var": "hero", "in": "@heroes", "steps": [ ... ]}}
  ]
}
```
- Шаги: `server` (RCON, опционально `expect` по ответу), `client`/`qa` (команда QA-драйвера), `chat`, `wait`, `key` (xdotool, `hold_ms ≥ 120`), `mouse`, `shot`, `expect` (регулярка по логу сервера или клиента от начала шага, таймаут), `metrics` (снимок TPS/MSPT/FPS/памяти с меткой), `include`, `foreach`, `note` (строка в отчёт). Подстановка `${var}`.
- Любая проверка с `"soft": true` не валит прогон, а попадает в отчёт как замечание.
- Таймауты: у шага (`timeout_s`) и у всего сценария.
- Данные героев (`tools/playtest/data/heroes.json`): ид героя, команда выбора, список действий и как их вызвать. Файл генерируется из кода (`HeroId`, `HeroAction`, определения героев) скриптом `tools/playtest/gen_data.py`, чтобы новые герои попадали в smoke сами.

## Готовые сценарии (`tools/playtest/scenarios/`)
1. `smoke-heroes.json` — для каждого героя: выбор, каждое действие (по одному нажатию и удержанию), скриншот, проверка, что в логах нет исключений и сервер не упал; второй клиент рядом смотрит (синхронизация, скриншот со стороны).
2. `world-events.json` — для каждого мирового события: старт → активная фаза → конец → очистка → повторный старт; проверки по статусу команд и логам.
3. `city-atheria.json` — Atheria в run-директории (скачивание по `AGENTS.md` §12, не коммитится), разрушение, `/city reset`, проверка восстановления по ответу команды и скриншотам до/после.
4. `quick.json` — 3-минутная проверка «сервер + 2 клиента вошли, герой выбран, способность сработала» для любой сессии.

## Метрики и отчёт
- Сервер: `forge tps` по RCON (TPS и mean tick ms по измерениям), RSS процесса.
- Клиент: `perfreset`/`perfstate` QA-драйвера (FPS, 1 %-low, p50/p99/max frame ms, heap), RSS процесса.
- Машина: `/proc/meminfo` (MemAvailable), загрузка CPU.
- Отчёт: `run-rig/reports/<время>-<сценарий>/report.md` + `report.json` + скриншоты (PNG, при необходимости уменьшенные) + выдержки логов (исключения, `ERROR`, `SUBPT`). Отчёт полного прогона публикуется в ветку `evidence/wave1-02`.

## Dev-команды за флагом
Стенду не нужна новая игровая логика. Если понадобится серверная dev-команда (например, «выбрать героя игроку без меню» уже есть в `/hero`), она регистрируется только при `-Dviltrumitecore.playtest=true` и в обычной игре отсутствует.

## Риски
- 4 ГБ RAM: два клиента + сервер могут не влезть даже без Gradle. Обход — урезанный `-Xmx`, низкая дальность, честная пометка в отчёте.
- Программный рендер: FPS не показателен для GPU; стенд сравнивает только прогоны на одной машине.
- QA-драйвер читает файл раз в 5 тиков: стенд ставит паузы ≥0,5 с между командами одному клиенту и ждёт строку `SUBPT ... exec` как подтверждение.
- Чужие баги не чиним: перечисляем в отчёте. Исключение — тривиальные блокеры запуска, отдельными коммитами.
